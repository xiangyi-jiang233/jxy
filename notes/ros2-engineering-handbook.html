01｜ROS 2 图与核心命令

ROS 2 图是运行中节点及其通信关系的集合。排查系统时，先确认“谁在运行、谁在发布、谁在订阅”。

节点 Node

承担单一、模块化职责的运行单元；一个进程可以包含一个或多个节点。

话题 Topic

用于连续数据流的异步发布/订阅通道，可有多个发布者和订阅者。

服务 Service

适合短时、同步的请求—响应操作。

动作 Action

适合耗时任务，能够提供反馈并支持取消。

从整体到局部的检查顺序

ros2 node list
ros2 node info <节点名>
ros2 topic list
ros2 topic info <话题名>
ros2 topic echo <话题名>
ros2 topic hz <话题名>
ros2 topic bw <话题名>
命令回答的问题
node list当前有哪些节点正在运行？
node info该节点发布、订阅、提供或调用什么？
topic info话题类型是什么？有几个发布者和订阅者？
topic echo消息内容是否真实到达？
topic hz当前订阅端实际观察到的消息频率是多少？
topic bw当前订阅端实际观察到的带宽是多少？
注意：hz 和 bw 是工具自身作为订阅者测得的结果，会受到设备性能、网络和 QoS 影响，不一定等于发布端理论值。

用 Foxglove 判断 ROS 2 数据是否真正更新

Foxglove 是可选的可视化与调试客户端，不是 Autoware 运行所必需的组件。它可以在另一台电脑上使用，但客户端必须能通过局域网、虚拟组网或其他路由访问运行 ROS 连接服务的主机；“不在同一局域网”本身不是唯一限制，关键是地址、端口和路由是否可达。

确认数据源区分实时连接与 MCAP/rosbag 录制文件
添加 Raw Messages选择目标话题，展开 header、数组和关键字段
判断是否更新同时观察消息时间、字段变化、频率和连接状态
追溯发布端用 ROS 2 CLI 确认节点、QoS 与数据来源

Raw Messages 面板怎么看

  1. 在布局中选择 Add panel，添加 Raw Messages。
  2. 在面板的数据路径或话题选择器中选中 <话题名>。
  3. 先展开 header，再根据消息类型检查点数组、位姿、速度或状态字段。
  4. Raw Messages 通常显示当前路径收到的最新消息；查看趋势时应改用 Plot，离散状态变化可用 State Transitions。
界面版本意识：按钮位置和数据路径语法可能随 Foxglove 版本变化，但核心步骤不变：连接数据源 → 添加面板 → 选择话题/字段 → 对照时间与内容。

sec、nanosec 为什么一直变化

ROS 2 时间通常由整数秒和不足一秒的纳秒部分组成：

消息时间（秒） = sec + nanosec × 10⁻⁹
0 ≤ nanosec < 1,000,000,000
  • nanosec 在连续消息之间频繁变化是正常现象；跨过整秒时，sec 增加，nanosec 重新从较小值开始。
  • 时间戳增加通常说明收到了带有新时间的消息，但不能单独证明轨迹内容发生变化。
  • 时间戳不增加也不能直接得出“没有生成轨迹”；还要检查播放是否暂停、连接是否中断、发布节点是否复用旧时间，以及消息数组和具体字段是否变化。
时间来源含义适合判断
Log time录制数据通常是原始记录时间；实时连接通常接近客户端收到消息的时间。播放排序和跨面板同步。
header.stamp由 ROS 消息生产链填写的业务时间。传感器、TF、定位和规划数据的时序关系。
播放游标时间当前录制文件的播放位置。判断文件是否正在播放，不能替代消息自身时间。

Trajectory 是实时的还是场景包里的

面板只能显示当前数据源提供的消息，不能仅凭轨迹形状判断来源。连接实时 ROS 系统时，它可能来自正在运行的规划节点；打开录制文件或运行数据回放时，它可能来自记录消息或由回放输入重新触发的规划结果。应追溯发布端和时钟：

ros2 topic info <轨迹话题> --verbose
ros2 topic hz <轨迹话题>
ros2 topic echo <轨迹话题> --once
ros2 node info <发布节点>

# 使用仿真时间时再检查
ros2 topic echo /clock --once
ros2 param get <发布节点> use_sim_time
  1. 确认 Foxglove 当前连接的是实时数据源还是录制文件。
  2. 查看轨迹话题的发布节点；没有发布者时，历史画面或最后一条消息不代表当前仍在规划。
  3. 检查时间戳、消息频率、轨迹点数量和点内容是否共同变化。
  4. 若使用 /clock，确认回放或仿真时钟正在推进。

连接中断的分层排查

数据源配置
  ↓
客户端到远端主机的网络可达性
  ↓
连接服务的进程与监听端口
  ↓
ROS 2 话题是否存在并持续发布
  ↓
QoS、TF 和消息时间是否适合可视化

远程桌面连接失败和 Foxglove 数据连接失败不是同一问题；前者影响操作远端图形界面，后者取决于数据服务、端口和网络路径。不要因为远控不可用就直接判定 ROS 2 节点或轨迹停止。

02｜TF2 与坐标变换

TF2 维护“某个坐标系相对另一个坐标系的位置与姿态”，让来自不同传感器的数据能在统一空间中使用。

内容含义
/tf持续变化的动态变换，例如车辆随时间移动。
/tf_static发布后保持不变的静态变换，例如传感器安装位置。
父子关系每条变换描述父坐标系与子坐标系之间的平移和旋转。
时间戳变换必须与传感器数据时间匹配，否则可能出现 extrapolation 错误。
ros2 topic info /tf
ros2 topic info /tf_static
ros2 topic hz /tf
ros2 run tf2_ros tf2_echo <源坐标系> <目标坐标系>
ros2 run tf2_tools view_frames

排查 TF 的四个问题

  1. 两个坐标系是否都存在？
  2. 中间的父子链路是否完整？
  3. 变换时间是否覆盖传感器消息时间？
  4. 静态变换是否误发到了动态通道，或反之？

03｜rosbag 与 MCAP

rosbag2 是 ROS 2 的录制与回放框架；MCAP 是它可以使用的一种存储格式。

选择话题只录制复现问题需要的数据
开始录制指定 MCAP 存储格式和名称
检查结果确认时长、话题和消息数量
回放验证确认数据可读且时间正确
# 录制指定话题
ros2 bag record -s mcap -o <记录名称> <话题1> <话题2>

# 录制全部话题
ros2 bag record -s mcap -o <记录名称> --all

# 查看与回放
ros2 bag info <数据包路径>
ros2 bag play <数据包路径>
ros2 bag play <数据包路径> --clock
占位符不是命令的一部分：不要把尖括号原样输入。例如把 <记录名称> 替换为 test_bag。Shell 会把尖括号理解为重定向符号。

--clock 会在回放时发布仿真时钟。只有使用仿真时间的节点设置正确时，它们才会按该时钟运行。

05｜MCAP 时间与切割

切割失败通常不是“文件坏了”，而是混淆了相对时间、Unix 时间戳、纳秒和时区。

时间形式示例含义特点
相对秒从录制开头算起的第 N 秒直观，但不能直接与真实日期混用。
Unix 秒从 1970-01-01 UTC 起累计的秒数可能包含小数部分。
Unix 纳秒Unix 时间乘以 10⁹精度高，应使用整数避免浮点误差。
RFC3339带日期、时间与时区偏移适合人类阅读，必须注意 Z 与本地偏移。

切割的正确顺序

读取范围确认原文件 start 与 end
统一时基把事件时间换成同一时区/单位
计算区间限制在原文件时间范围内
验证输出检查消息数、时长和话题
# 显示格式只影响输出，不修改文件内时间
mcap info --time-format=rfc3339 <输入.mcap>
mcap info --time-format=nanoseconds <输入.mcap>

# 参数名称以本机版本帮助为准
mcap filter --help

输出为 0 条消息时检查

  1. 切割区间是否真正落在原文件 start 与 end 之间。
  2. 是否把本地时间误当成 UTC，或重复加减时区偏移。
  3. 是否把秒当成纳秒，或把纳秒当成秒。
  4. 筛选的话题是否存在，并且在该区间确实有消息。
  5. 输出后是否再次运行 mcap info 和 mcap doctor。

06｜可复用 Python 命令行工具

把一次性脚本做成工具，关键不是代码变长，而是输入明确、校验完整、错误可理解、结果可验证。

模块适合解决的问题
argparse定义位置参数、可选参数、默认值、帮助文本和互斥参数。
pathlib.Path跨平台地组合、检查和遍历文件路径。
datetime / ZoneInfo处理日期、时区与时间戳转换。
subprocess.run调用外部 CLI，并检查返回码、标准输出和错误输出。
shutil复制、移动文件和目录等高层文件操作。
re从结构稳定的文本输出中提取字段。

推荐处理流程

解析参数
  ↓
检查输入与参数范围
  ↓
读取源数据元信息
  ↓
统一时间单位并计算区间
  ↓
执行切割或复制
  ↓
验证输出消息数与时间范围
  ↓
返回清晰的成功或错误信息
原始消息复制：如果目标只是按时间截取数据，通常不必解析图像、点云或自定义消息内容。复制序列化 payload 能降低依赖和类型兼容风险。

接口设计原则

  • 同一含义只提供一个明确入口，冲突参数使用互斥组。
  • 危险覆盖必须显式使用 --force 或 --overwrite。
  • 时间窗口、输入路径和输出路径都在执行前校验。
  • 外部命令失败时保留返回码和关键错误信息。
  • 输出为空也应被视为需要解释的结果，而不是静默成功。

07｜Docker 与文件流转

宿主机和容器拥有不同文件系统视图。复制前必须明确源在哪一侧、目标在哪一侧。

docker ps
docker exec -it <容器名> bash

# 宿主机 → 容器
docker cp <宿主机文件> <容器名>:<容器目录>

# 容器 → 宿主机
docker cp <容器名>:<容器文件> <宿主机目录>
方式适用场景特点
docker cp临时复制单个文件或目录。容器运行或停止时均可使用；必须同时给出源和目标。
绑定挂载需要长期共享、频繁读写的数据目录。宿主机目录持续映射到容器。
容器内 cp文件已经在容器内部，只需换位置。不能直接访问未挂载的宿主机路径。
常见错误：只写一个路径时，docker cp 无法判断要从哪里复制到哪里；目标父目录不存在时也可能失败。

08｜Linux 路径与软链接

软链接类似“可重定向的快捷入口”，适合稳定入口指向不同版本或资源目录。

pwd
readlink <链接路径>
readlink -f <链接路径>
ln -s <目标路径> <链接路径>
rm <链接路径>
命令作用
readlink显示软链接中直接保存的目标。
readlink -f递归解析软链接和相对路径，输出最终绝对路径。
rm <链接>删除链接本身，不删除链接指向的真实目录。
修改前检查：先用 ls -l 和 readlink -f 确认当前指向。创建同名新链接前，应明确旧路径是链接、普通文件还是目录。

09｜DDS、RMW 与 CycloneDDS

ROS 2 的通信问题需要分层判断，不能看到节点异常就直接归因于应用代码。

ROS 2 应用节点、话题、消息类型、命名空间和 QoS。
RMWROS 2 与具体中间件实现之间的抽象接口。
CycloneDDS负责发现、发布/订阅、网络接口和传输配置。
操作系统网卡、路由、多播、防火墙、Socket 缓冲区和内核限制。
echo "$RMW_IMPLEMENTATION"
echo "$CYCLONEDDS_URI"
ip addr
ip route
sysctl net.core.rmem_max
ros2 node list
ros2 topic list

话题存在但收不到数据：先核对 QoS

ROS 2 端点只有在请求与提供的 QoS 兼容时才会建立通信。因此，“话题能列出来”只证明发现了名称，不证明订阅者一定能收到消息。

ros2 topic info <话题名> --verbose
ros2 node info <节点名>

# 临时订阅测试前先查看本机参数支持
ros2 topic echo --help
ros2 topic echo <话题名> --qos-reliability best_effort
策略含义常见兼容关系
Reliabilityreliable 重试以提高送达保证；best_effort 更重视及时性，可容忍丢包。Best Effort 发布者不能满足 Reliable 订阅者；Reliable 发布者可以满足 Best Effort 订阅者。
Durabilityvolatile 只发送当前连接后的样本；transient_local 可为后加入的订阅者保留历史样本。Volatile 发布者不能满足要求 Transient Local 的订阅者；反向通常兼容。
History / Depthkeep_last 只保留最近 N 条；Depth 决定 N。主要影响排队与丢弃行为；队列太小可能丢旧消息，但不能替代 Reliability。
确认名称与类型排除拼写、命名空间和消息类型错误
查看端点检查发布者、订阅者及各自 QoS
做匹配测试用临时订阅者调整 QoS 验证假设
再查底层确认 DDS、域、网卡、容器和防火墙
当前学习边界：已掌握检查方法，但尚未记录真实话题的执行输出，因此不能把某次通信异常直接归因为 QoS。必须以 --verbose 的端点信息和匹配试验为证据。

依据：ROS 2 Humble QoS 设置与 ROS 2 话题检查命令。

多网卡与自动选择

CycloneDDS 会根据接口状态、地址类型和多播能力选择网络接口。存在 Wi-Fi、有线、VPN、容器网桥等多张网卡时，自动选择可能不符合实际通信需求，此时应在配置中明确指定接口。

参与者索引耗尽

同一 DDS 域中，每个进程都需要一个参与者身份。若配置固定索引、索引范围过小，或旧进程尚未退出，可能出现 Failed to find a free participant index for domain。

  1. 先确认同一域中是否残留多个 ROS 2 / Autoware 进程。
  2. 检查 CycloneDDS 配置中的 ParticipantIndex 与自动索引上限。
  3. 需要自动分配时，可使用 ParticipantIndex=auto，并按实际并发规模设置合理的 MaxAutoParticipantIndex。
  4. 配置修改后重启相关进程，再用节点和话题列表验证。
不要混淆两类问题：参与者索引耗尽属于 DDS 身份分配；“接口不支持多播”属于网络接口能力。修改 ParticipantIndex 不会修复多播问题。

Socket 接收缓冲区

CycloneDDS 可以请求扩大 Socket 接收缓冲区。如果配置中的最小值高于操作系统允许的上限，DDS 初始化可能报告错误。通用处理方法是：

  1. 读取 CycloneDDS 配置要求的最小缓冲区。
  2. 使用 sysctl net.core.rmem_max 查看内核上限。
  3. 确认错误确实来自两者不匹配，而非先盲目修改。
  4. 由系统管理员按数据量和安全要求调整内核参数。
  5. 重新启动进程，并用节点与话题列表建立基线。
不要照抄单机数值：合理缓冲区取决于消息大小、频率、并发话题、内存和网络环境。知识库只保存判断方法，不固化某台机器的参数。

10｜通信中间件性能比较

“某中间件一定更快”通常缺少条件。性能结论必须说明消息、进程、机器、传输方式和测试指标。

维度需要比较的内容
部署范围进程内、同机进程间，还是跨机器通信。
数据规模小控制消息还是大图像、点云。
复制次数是否使用共享内存、零拷贝，是否发生序列化。
实时性平均延迟、尾延迟、抖动和丢包。
资源消耗CPU、内存、网络带宽与线程调度成本。
功能成本发现机制、QoS、跨平台互操作和可配置性。

Cyber RT 针对 Apollo 的模块组织、调度和通信进行了深度整合，在特定部署中可能减少通用框架开销；DDS 提供标准化发布/订阅、发现与 QoS，适合多实现互操作。最终应以同一硬件、同一消息和同一指标进行实测，而不是只比较框架名称。

11｜远程开发环境识别

同一块屏幕里可能同时存在本地电脑、远程主机和容器。多数“路径不存在”或“代理无效”都来自环境判断错误。

层级常见职责需要确认

代理开启时访问内网服务

内网、虚拟组网或本地开发服务通常不应绕到公网代理。通用做法是在代理客户端中建立直连规则，并确保它们排在兜底代理规则之前。

  1. 先判断目标是域名还是 IP；域名还要确认最终解析地址。

  3. 规则顺序遵循“更具体的直连规则在前，最终 MATCH / 默认代理在后”。
  4. 若客户端启用 TUN、Fake-IP 或远程 DNS，需同时检查 DNS 解析和路由结果。
  5. 修改后分别用域名和解析后的 IP 测试，确认请求没有被错误送入代理。

从分层架构定位到具体源码包

Autoware 采用分层、组件化架构。官方架构视图包含七个功能栈；它们通过 ROS 2 接口协作，因此排障时既要知道异常属于哪一层，也要沿话题和 TF 检查层间输入输出。

功能栈主要职责场景复现时关注
Sensing接入并预处理相机、LiDAR、雷达、GNSS、IMU 等传感器数据。时间戳、坐标系、数据频率和驱动状态。
Map提供道路语义、车道几何及可选的点云地图。地图版本、坐标基准、车道关系和地图入口。
Localization估计车辆位姿、速度和运动状态。初始位姿、定位跳变、速度与 TF 连续性。
Perception从传感器数据提取目标、障碍物、交通信号等环境语义。目标是否存在、类别/位置/尺寸/预测是否正确。
Planning根据路线、地图、车辆状态和环境信息生成行为路径与轨迹。模块状态、候选路径、安全检查、批准/取消原因。
Control跟踪规划轨迹并生成纵向、横向控制指令。轨迹误差、控制延迟、转向和加减速响应。
Vehicle Interface连接通用控制命令与具体车辆底盘，并回传车辆状态。命令是否下发、执行器状态、限幅和反馈。
不要把七层当成单向直线：地图会同时服务定位、感知和规划，车辆状态也会反馈给定位与控制。七层更适合用来界定职责和接口，而不是代替实际 ROS 2 计算图。

Sensing、Localization、Perception、Trajectory 与 Control 的边界

概念它负责什么容易混淆的地方
Sensing驱动传感器并完成解码、校正、同步、过滤等预处理。它不是“把所有环境数据统一转换到世界坐标系”的单一模块；具体节点会借助 TF 把数据变换到算法需要的坐标系。
Localization利用 GNSS、IMU、轮速、点云匹配或其他信息估计主车位姿与运动状态。定位描述的是“自车在哪里、怎样运动”，不是识别外部障碍物。
Perception把传感器观测转成目标、车道、信号灯和预测轨迹等环境语义。感知结果可以位于自车或世界相关坐标系；应以消息 frame_id 和 TF 为准。
Trajectory规划器给出的目标运动序列，通常包含位置、姿态、速度和加速度等期望值。它是“准备怎样走”，不是车辆已经执行的真实运动。
Control比较当前车辆状态与目标轨迹，计算转向、加速和制动命令。轨迹正确但车辆没有按轨迹行驶时，应继续检查控制与车辆接口。

odom 从哪里来

odom 既可以指坐标系，也经常出现在 nav_msgs/msg/Odometry 类型的话题名中。它不是固定由某一个传感器直接产生：轮速积分、视觉/激光里程计、IMU 融合、状态估计器或仿真器都可能提供里程计信息。

  • header.frame_id 表示位姿所参考的坐标系。
  • child_frame_id 表示速度所关联的车体坐标系。
  • pose 表示位置与姿态，twist 表示线速度与角速度；协方差描述估计不确定性。
  • Autoware 中常用的车辆运动状态通常已经经过定位或状态估计链处理，不能仅凭话题名断定它来自 GNSS、IMU 或轮速。
ros2 topic type <里程计话题>
ros2 topic info <里程计话题> --verbose
ros2 interface show nav_msgs/msg/Odometry
ros2 node info <发布节点>
频率不能凭模块名称猜：定位、感知和规划的实际频率取决于传感器、节点配置、输入触发方式和运行负载。应使用 ros2 topic hz 在当前环境实测，并记录测量条件。

// 通用化示例：名称和话题均为占位形式

: Node("example_node", options),
  diagnostics_(std::make_unique<DiagnosticsInterface>(this, "<诊断模块名>"))

逐句识别核心 C++ 语法

源码形式含义阅读时要问
: member_(...)构造函数初始化列表，在进入函数体前构造基类和成员对象。这个成员是节点运行前必须具备的依赖吗？
this / *thisthis 是当前对象指针，*this 是当前对象本身。辅助类为什么需要访问当前 ROS 2 节点？
const auto value = ...让编译器推导类型，并禁止后续通过该变量修改对象。实际返回类型可否从函数声明或编辑器跳转确认？
std::make_unique<T>创建由一个 unique_ptr 独占管理的对象。该资源是否只属于当前节点？
std::make_shared<T>创建可由多个 shared_ptr 共同持有的对象。哪些组件需要共享它，生命周期由谁决定？
function<Type>(...)尖括号是模板参数；ROS 2 常用它指定消息或参数类型。Type 是哪一个消息/数据类型？
std::placeholders::_1配合 std::bind 表示回调被调用时传入的第一个参数。它最终绑定到哪个成员函数和哪种消息？
智能指针的学习重点是所有权：unique_ptr 表达“只有一个所有者”，shared_ptr 表达“多个对象共享生命周期”。先判断谁拥有资源，再记语法，比把二者都理解成“高级指针”更有用。

ROS 2 API 在构造函数中的作用

API作用常见误解
declare_parameter<double>("<参数名>")声明参数并取得其有效值；类型在编译期确定。声明参数不等于参数一定来自 YAML，还应沿 launch、参数文件和默认值确认来源。
create_publisher<Trajectory>(...)创建指定消息类型的发布器。创建 Publisher 不代表已经发送消息；还要找到 publish(...)。
create_subscription<Trajectory>(...)创建订阅器，并把收到的消息交给回调函数。订阅存在不代表能收到数据，还受话题解析、消息类型和 QoS 兼容性影响。
"~/output/trajectory"~ 表示节点私有命名空间，最终完整话题名取决于节点名、namespace 和 remapping。不能只凭源码字符串猜运行时完整话题。
1这里通常表示 QoS 队列深度。它不是发布频率，也不表示只发布一次。

  3. 从 declare_parameter 追踪三个关键参数真正参与计算的位置。
  4. 从 publish 找到输出消息如何构造。
  5. 用运行时话题和参数验证源码理解；版本、remapping 和 YAML 都可能改变实际行为。
当前能力边界：读懂构造函数、Publisher、Subscription 和 Callback，说明已经能从运行接口进入源码；只有继续讲清核心处理及用输入/输出数据验证结果，才算完成一个模块的源码阅读闭环。

参考：ROS 2 Humble 的 rclcpp::Node API与 C++ Publisher/Subscriber 教程；C++ 参考的 make_unique、make_shared与 std::bind。

Behavior Path Planner 在规划栈中的位置

behavior_path_planner 属于行为规划：它根据路线、地图、车辆状态和周围目标选择合适的场景模块，生成行为路径、可行驶区域和转向灯命令。典型场景模块包括车道跟随、变道、静态障碍物避让、起步和目标停车。

Planner Manager 负责激活适合当前场景的模块、管理多个模块的执行顺序，并把模块输出组织为可执行路径。调试“变道没有触发或时机不一致”时，应同时检查：

  1. 感知目标、地图路线、车辆位姿与速度等输入是否在同一时间轴上有效。
  2. 目标场景模块是否已注册、请求执行、等待批准、被拒绝或被取消。
  3. 参考路径、候选路径和最终路径在哪一步开始分叉。
  4. 路径已经正确但车辆未跟随时，再转向运动规划、控制和车辆接口排查。
当前学习边界：能够定位包根目录并识别文件职责，不等于已经读完该模块。只有解释清楚输入、输出、启动配置、关键状态和一条真实执行路径，才算完成模块级学习。

参考：Autoware 架构概览、Behavior Path Planner与 ROS 2 包目录约定。

Header、时间与坐标系

字段含义排查重点
header.stamp.sec时间戳的整数秒部分。组合时间为 t = sec + nanosec × 10⁻⁹ 秒。对齐传感器、感知、规划数据时应比较消息时间，而不是终端显示时间。
header.stamp.nanosec不足一秒的纳秒部分。
header.frame_id该数据关联的坐标系。核对 TF 树中是否存在该坐标系、变换方向是否正确、变换时间是否覆盖消息时间。

时间戳回答“这份数据何时有效”，frame_id 回答“数值在哪个坐标系中解释”。只核对数值而忽略这两项，容易把正常目标误判为位置跳变或轨迹错位。

PredictedObjects 的嵌套结构

集合层std_msgs/Header header 描述整批对象的时间与坐标系，PredictedObject[] objects 保存零个或多个目标。
对象层object_id 用 UUID 标识对象；同时包含存在概率、分类数组、运动学状态与形状。
分类层每项包含类别标签和概率。分析时应查看完整概率分布及生产节点规则，不能只看数组位置或把编号直接当成人类可读类别。
运动层位姿、速度、加速度、预测路径及其置信度用于描述“现在在哪里、怎样运动、未来可能去哪”。字段以实际消息版本为准。
类别组典型标签通用解释
交通参与者TRAILER、MOTORCYCLE、BICYCLE、PEDESTRIAN挂车、摩托车、自行车和行人。
项目或版本扩展CONSTRUCTION_VEHICLE、BARRIER、TRAFFIC_CONE、ANIMAL、HAZARD工程车辆、隔离设施、交通锥、动物或其他危险物；是否存在及编号取决于消息版本。
可通行关系OVER_DRIVABLE、UNDER_DRIVABLE表示可从物体上方压过或从其下方通过的语义分类；具体安全条件必须由当前消息定义和下游规划规则确认。

covariance[36] 表示什么

ROS 几何消息常把 6×6 协方差矩阵按行展开为 36 个数。对位姿，变量顺序通常是 (x, y, z, 绕 X 旋转, 绕 Y 旋转, 绕 Z 旋转)；速度协方差则对应线速度与角速度。使用前必须查看具体字段的消息定义。

位置含义读法
对角线每个变量的方差。标准差为 σ = √variance；方差越大通常表示该维估计越不确定。
非对角线两个变量之间的协方差。反映误差是否共同变化；不能在不知道变量顺序时直接解释。
全零矩阵数值为零，但语义取决于发布节点约定。不要自动解释为“完全准确”；应查发布节点、接口约定和上游传感器是否真实提供不确定性。

协方差可被定位融合、目标跟踪、数据关联、异常值门限和规划安全裕度等环节使用，但每个节点是否消费该字段、如何消费，必须沿订阅者源码或文档验证。

轴距与转弯：把“转弯更慢”说准确

在简化 Ackermann 自行车模型中，若前轮转角 δ 和车速 v 相同，轴距 L 越长，曲率和横摆角速度越小，转弯半径越大：

曲率：κ = tan(δ) / L
转弯半径：R = L / tan(δ)
横摆角速度：r = v · tan(δ) / L

因此“轴距越长，转弯越慢”只是在相同车速与转角条件下的简写。轴距会影响最小转弯半径、轨迹可行性、控制器参数和仿真一致性；它是车辆物理参数，不应为了掩盖规划或控制问题而随意调节。

参考：ROS 2 的 Header、PoseWithCovariance，Autoware 的 PredictedObjects、ObjectClassification与 Ackermann 运动学约束。

起点、终点与 Pose 四元数

规划任务中的起点和终点都不是单独的三维坐标，而是包含位置与朝向的 Pose。手动设置终点后，应优先查看系统实际接受并发布的路线或路由状态消息，而不是只依据 RViz 中的箭头位置判断。

字段含义常见误解
position.x/y/z在 header.frame_id 指定坐标系中的位置。z 是高度，不是航向角。
orientation.x/y/z/w描述三维旋转的单位四元数。w 不是第四个空间坐标；orientation.z 也不等于 yaw。
start_pose路线计算使用的起始位姿；具体来源可能是当前定位或接口提交值。不能只凭界面标记断定系统采用了哪个起点。
goal_pose规划目标的位置和到达朝向。只设置位置而忽略方向，可能造成终点附近路径方向不符合预期。

  2. 如果路线消息只提供目标，则分别读取当前定位 Pose 和目标 Pose，并记录同一时刻的数据。

  4. 路线消息存在不等于路线有效，还应检查路由状态、发布节点和规划输出是否更新。

为什么姿态有 w

四元数写作 q = (x, y, z, w)，通常要求归一化，即 x² + y² + z² + w² = 1。对于只绕竖直轴旋转的平面车辆，可用下面的关系理解：

x = 0
y = 0
z = sin(yaw / 2)
w = cos(yaw / 2)
  • 无旋转时常写成 (0, 0, 0, 1)；四项全为零不是有效单位四元数。
  • q 与 -q 表示相同姿态，因此四个分量不必逐项唯一。
  • 如果界面里“没有 w”，先确认当前展开的是 position 还是 orientation，以及面板是否把四元数转换成了 yaw 或折叠了字段。
  • 用 ros2 interface show <消息类型> 检查定义，再用 Raw Messages 或 ros2 topic echo 查看原始数据；显示不完整不能直接推断消息没有该字段。

规划子模块如何分工

  • mission_planner 负责从起点、目标点和地图生成全局路线，不直接完成局部避障。
  • behavior_path_planner 负责横向行为与场景选择，例如车道跟随、变道和避让，并管理模块的请求、批准、执行与结束状态。
  • elastic_band_smoother、path_optimizer 等路径处理模块改善几何连续性和车辆运动学可行性；具体启用哪个模块由版本和启动配置决定。
  • behavior_velocity_planner 根据交通规则与场景在路径上加入停车、减速等速度约束。
  • motion_velocity_planner 等纵向运动规划模块综合障碍物、限速以及加速度/加加速度约束，生成可执行速度曲线。
  • planning_evaluator 用指标观察规划结果；simple_planning_simulator 用于简化车辆运动响应。它们分别属于评估和仿真辅助，不应与主规划器职责混淆。
Path 与 Trajectory 的直观区别：Path 更侧重“空间上走哪里”和可行驶边界；Trajectory 在此基础上进一步给出时序相关的速度、加速度等可执行信息。具体字段仍以当前消息定义为准。

Scenario Selector 选择的是场景，不是“最安全路径”

Scenario Selector 的典型职责是在车道行驶、停车等高层场景之间切换下游使用的 Trajectory。它可以结合路线、地图、车辆状态和各场景轨迹判断当前应激活哪个场景，但不是把同一场景生成的多条候选路径逐条评分后选出“最安全的一条”。

不要混淆两种选择：场景切换解决“现在运行哪类规划器”；候选路径评估解决“该场景内部哪条方案满足安全、法规和运动学约束”。后者通常由 Behavior Path Planner 的具体场景模块及其安全检查完成。
数据层级本质典型作用
Lanelet / 地图道路带交通规则和拓扑关系的道路元素。描述车道连接、边界、限速和可通行关系。
Route从起点到目标点的一组路线段。约束全局任务应经过哪些道路区域。
Path按顺序排列的路径点及可行驶区域。表达局部几何方案与横向行为；它是“点序列表示的路”，不是地图道路本体。
Trajectory带速度、加速度等执行信息的有序轨迹点。作为控制器需要跟踪的时空参考。

在可视化工具里看到 points[]，说明消息在数据结构上由点组成；把这些点按顺序连接后，才形成 Path 或 Trajectory。判断是否存在多条候选方案，应查看候选话题、模块状态和各候选消息，不能把一条消息里的多个点误认为多条路。

ros2 topic list | grep -E 'candidate|reference|path|trajectory'
ros2 topic info <候选路径话题> --verbose
ros2 topic echo <候选路径话题> --once

参考：Autoware 的 Scenario Selector 接口说明与 Behavior Path Planner。

候选路径、准备段与最终路径

候选路径是场景模块提出、但尚未必被批准为最终输出的方案。以变道为例，调试时应分别记录“首次产生候选”“通过安全检查”“获得批准”“进入横向移动”“取消或完成”的时间，而不是只看车辆是否已经横移。

prepare_duration 常用于描述横向移动前的准备时间。在速度近似稳定时，准备段纵向距离可粗略理解为 d ≈ v × t；时间增大通常会让正式横移开始得更晚、准备距离更长，但最终效果还受车辆速度、路线剩余距离、安全检查、采样范围和版本实现共同影响，不能只凭单个参数判断根因。

用话题把现象定位到具体阶段

# 再检查实际字段和一条样本

  2. 上游正确、候选路径未产生：检查路线、地图、模块激活条件和请求状态。
  3. 有候选但未成为最终路径：检查安全判定、批准状态、取消原因和模块竞争。
  4. 最终路径正确、Trajectory 异常：转向路径优化或速度规划。
  5. Trajectory 正确但车辆响应异常：转向控制、车辆接口、延迟和车辆模型。

版本清单导入与 colcon 编译

制作可复现的 Autoware 场景包时，必须把“当前版本、目标版本、源码清单、编译结果、重跑结果”分开记录。仅切换目录名或只看到脚本启动，不足以证明版本适配完成。

用 vcstool 导入多个仓库清单

# 每份清单是一次独立命令

vcs import <源码目录> --recursive < <仓库清单1.repos>

vcs validate < <仓库清单2.repos>
vcs import <源码目录> --recursive < <仓库清单2.repos>

  2. --symlink-install 尽可能用符号链接安装，便于开发迭代；--cmake-args 把参数传给 CMake 包。
  3. --packages-up-to 构建目标包及其依赖；--packages-skip 只应跳过已确认非必需或当前环境无法支持的包。
  4. 判断成败应看最终 Summary、失败包和退出状态；出现 stderr 不一定等于整个工作空间失败，但必须阅读内容。
  5. 编译成功后重新加载 install/setup.bash，再检查关键包、启动文件和场景重跑结果。

16｜实车数据回放与闭环仿真一致性

仿真与实车使用相似地图和轨迹，并不保证车辆会在同一时刻变道。轨迹差异常由时间、状态机、纵向速度和车辆动力学在闭环中共同累积。

先区分三种“看起来一样”

对齐对象真正需要一致的内容
几何轨迹道路、车道线、目标路径和坐标变换。
时间过程起始时刻、消息时间戳、回放倍率、延迟和插值。
闭环状态速度、加速度、航向、转角、障碍物、规划状态和控制反馈。
核心判断：若早期候选变道轨迹能够重合，随后仿真恢复直行而实车继续横移，问题通常不只是地图几何误差，更可能是规划状态、触发条件、速度演化或控制反馈已经分叉。

为什么固定速度会改变变道结果

固定下发速度会改变车辆纵向位置、到达触发点的时刻、与周围目标的相对距离、TTC、可接受间隙和状态机条件。即使横向路径完全相同，仿真车辆也可能因为“更早或更晚到达某个判断位置”而在不同时间批准变道。

需要复现实车时，应优先回放实车速度、加速度和姿态状态，或使用与实车一致的闭环车辆模型；不能只固定一个速度值后比较最终轨迹。

差异来源与观察信号

层级常见原因应比较的信号
时间同步起始偏移、时间戳基准不同、回放倍率或消息延迟。原始时间戳、仿真时钟、关键事件相对时间。
初始状态初始位置、航向、速度或所在车道不一致。位姿、纵向速度、横向速度、航向角和 yaw rate。
行为规划可变道判断、批准、取消、迟滞或安全间隙不同。变道状态、原因码、目标车道、碰撞检查和安全间隙。
感知预测目标位置、速度、预测轨迹或消息丢失不同。目标列表、预测轨迹、相对距离、TTC 和 QoS。
控制与车辆转向延迟、执行器滞后、限幅、轮胎和车辆模型不同。控制指令、转角反馈、加速度反馈和横向误差。

推荐诊断顺序

统一时间轴对齐起点、时钟和关键事件
统一初始状态位置、航向、速度和车道
比较状态机何时申请、拒绝、批准或取消
隔离动力学再检查控制延迟和车辆模型
  1. 选取同一个关键事件作为零时刻，不只按视频画面或文件起点对齐。
  2. 叠加比较速度、加速度、航向角、yaw rate 和横向偏移。
  3. 记录规划器第一次产生变道候选、第一次拒绝和最终批准的时间及原因。
  4. 核对同一时刻的障碍物、预测轨迹、间隙和安全阈值。
  5. 最后再调整转向延迟、执行器响应、加减速度限制和车辆参数。

最小对照实验

  • 实验 A：固定速度与回放实车速度对比，只改变纵向输入。
  • 实验 B：固定规划输入，比较开环轨迹回放与完整闭环仿真。
  • 实验 C：暂时理想化执行器延迟，判断偏差主要来自规划还是控制。
  • 实验 D：固定同一障碍物序列和初始状态，逐项恢复感知、预测和动力学差异。
一次只改一个变量：同时修改速度、规划阈值和车辆模型，会让结果无法归因。每次实验都应保存输入、配置、关键时间点和输出轨迹。

17｜Excel 长数字、科学计数法与精度

从网页、日志或数据库复制长编号到 Excel 时，先判断它是“用于计算的数值”还是“必须逐位保真的标识符”。编号、序列号、长时间戳等通常应按文本保存。

先区分显示变化与数据变化

现象含义处理方式
显示为 8.98609E+19E+19 表示乘以 10 的 19 次方。常规格式会对很大的数使用科学计数法。先查看编辑栏中的实际内容，再判断是否只是显示方式变化。
编辑栏仍保留完整且正确的 15 位以内数值通常只是单元格宽度或数字格式导致的显示变化。加宽列，或按用途改为“数值”等格式。
长编号超过 15 位，末尾已经变为 0 或发生变化Excel 已把文本式编号当作数值处理，并触发数值精度限制。从原始来源重新复制或导入；只修改显示格式无法恢复已丢失的位。
关键限制：Excel 数值最多保留 15 位有效数字。16 位及以上的编号不能依赖数值格式保真，应在写入前设为文本。

安全录入长编号

判断用途需要运算，还是只需逐位保存
预设文本粘贴前把目标列设为“文本”
写入数据单条可在前面输入英文单引号

  • 批量粘贴：先选中空列，按 Ctrl+1 打开“设置单元格格式”，选择“文本”，再粘贴。
  • 单条输入：在编号前输入英文单引号，例如 '<长编号>；单引号只用于告诉 Excel 按文本处理。
  • CSV 或外部数据：使用“数据 → 从文本/CSV”等导入流程，并把编号列的数据类型明确设为文本。不要先让 Excel 自动转换，再尝试补救。

发现异常后的恢复顺序

  1. 不要继续保存覆盖唯一的原始文件，先保留原始网页、CSV、日志或数据库查询结果。
  2. 在编辑栏中查看实际值，并与原始来源逐位比较；仅看单元格显示不够。
  3. 如果第 16 位之后已经变化，删除错误列，把空列预设为文本，再从原始来源重新导入。
  4. 抽查字段长度、前几位和末几位；批量数据可用源系统的字符串长度或校验规则验收。
不要把格式化当成恢复：加宽列、改为“数值”或使用 TEXT() 只能改变当前值的显示或类型，不能找回已经被数值转换丢失的原始数字。

更新远端信息并安全切换已有测试分支

git fetch 只下载远端引用并更新 origin/<分支> 等远端跟踪分支，不会把内容合并进当前分支；git pull 会先 fetch，再把当前分支的上游分支整合进当前分支。因此只想查看新分支或确认远端状态时，先用 fetch 更容易控制影响。

# 先保护工作区并刷新远端分支列表

git branch -r

# 远端分支尚无同名本地分支时
git switch --track origin/<目标分支>

# 已有同名本地分支时
git switch <目标分支>
git branch -vv

# 仅允许快进，避免无意生成合并提交
git pull --ff-only
切换前先看 git status：未提交修改可能阻止切换或被带到目标分支。不要用 git switch --discard-changes 或其他强制选项掩盖问题；应先明确提交、暂存备份或人工处理这些修改。

多仓库更新“卡住”时如何判断

多仓库工具可能长时间停留在某个仓库的最后一条输出；“HEAD is now at …”只表示该仓库已切到某个提交，后续静默不等于一定卡死。先判断进程是否仍在运行、网络是否有流量、是否等待认证或代理超时，再决定是否中断。

  1. 保留当前终端，在另一个终端查看相关 Git/SSH 进程及资源活动。
  2. 区分错误类型：DNS、连接超时和 443 不可达优先查网络/代理；Permission denied (publickey) 优先查 SSH 身份与仓库权限。
  3. 确认进程已退出后，只重试失败的仓库或原更新命令；不要在未知状态下并发启动多次更新。
  4. 需要代理时使用占位配置，并在当前 Shell 或 Git 配置中核对实际生效值：
export http_proxy=http://<代理IP>:<代理端口>
export https_proxy=http://<代理IP>:<代理端口>

git config --get http.proxy
git config --get https.proxy

SSH 密钥解决身份认证，代理解决网络可达性；二者可能同时需要，但不能互相替代。Issue 中只记录错误类别、验证命令、处理步骤与结果，不公开真实代理地址、用户名、密钥或内部仓库名。

参考：Git 官方的 git fetch、git pull与 git switch。

账号或仓库改名后 GitHub Pages 无法访问

账号或仓库名称变化会同时影响仓库命名空间、默认 Pages 地址、外部链接和本地远端配置。普通仓库链接通常会自动重定向，但 Pages 地址和写死的旧名称仍应逐项核对。

确认新地址检查新 owner、仓库名和 Pages URL
检查发布配置核对 Settings → Pages 的来源
检查工作流查看最新 Actions 构建与部署结果
触发并验证重新部署后访问新地址和关键页面
# 本地仓库仍指向旧账号或旧仓库名时
git remote -v
git remote set-url origin https://github.com/<新用户名>/<仓库名>.git
git remote -v

# 如果工作流声明了 workflow_dispatch，可在 GitHub Actions 页面手动运行
# 如果使用分支作为发布源，向该发布分支提交后会创建新部署
  1. 先打开 https://github.com/<新用户名>/<仓库名>，确认仓库已位于新命名空间。
  2. 项目站点通常使用 https://<新用户名>.github.io/<仓库名>/；同时搜索 README、HTML、配置文件和工作流中是否仍写着旧用户名或旧 URL。
  3. 在仓库 Pages 设置中确认发布源：GitHub Actions 或指定分支/目录，并检查是否仍处于已发布状态。
  4. 查看 Actions 中最近一次构建和部署。失败时先读具体步骤日志，不要仅凭网页 404 判断源码有问题。
  5. 需要重新部署时，优先重新运行支持 workflow_dispatch 的工作流；分支发布则提交到发布源。重新部署后检查首页、子页面、静态资源和页内链接。
  6. 若使用自定义域名，还要核对 DNS、仓库中的 CNAME 和 HTTPS 状态是否指向新命名空间。
区分重定向与修复：旧仓库链接暂时能跳转，不代表配置已更新。GitHub 建议改名后更新本地 remote；Pages 恢复则要以成功部署记录和新 URL 实际可访问为准。

连接 GitHub 失败时的代理判断

git config --global --get http.proxy
git config --global --get https.proxy

# 代理程序与 Git 在同一系统中运行时
git config --global http.proxy http://127.0.0.1:<代理端口>
git config --global https.proxy http://127.0.0.1:<代理端口>

# 不再需要代理时
git config --global --unset http.proxy
git config --global --unset https.proxy
  • 127.0.0.1 表示“当前运行 Git 的系统自身”，不是局域网网卡地址。
  • Git 与代理客户端在同一 Windows 或 Linux 系统时，通常不应把 127.0.0.1 替换成本机局域网 IP。
  • Git 若运行在容器、虚拟机、WSL 或远程主机中，它们的 127.0.0.1 指向各自环境；此时应确认代理监听地址、端口、防火墙和宿主机可达地址。
  • Failed to connect to github.com:443 只能说明 HTTPS 连接未建立，仍需分别检查 DNS、路由、代理是否监听以及 Git 代理配置。

19｜SPI 同步串行通信

SPI（Serial Peripheral Interface）是嵌入式系统常用的同步串行总线。控制器产生时钟并选择目标设备，数据通常在 MOSI 与 MISO 上同时移位。

四根核心信号线

信号方向与作用
SCLK / SCK由控制器产生时钟，决定每一位数据何时改变和采样。
MOSIController Out, Peripheral In；控制器发送给外设的数据。
MISOController In, Peripheral Out；外设返回给控制器的数据。
CS / nCS片选信号，常为低有效；一个总线连接多个外设时，通常每个外设需要独立片选。
全双工：每产生一个时钟，控制器在 MOSI 移出一位的同时，也会在 MISO 移入一位。即使只想读取，也常需要发送占位字节来产生时钟。

SPI 模式：CPOL 与 CPHA

模式CPOLCPHA含义
Mode 000时钟空闲为低，在第一个边沿采样。
Mode 101时钟空闲为低，在第二个边沿采样。
Mode 210时钟空闲为高，在第一个边沿采样。
Mode 311时钟空闲为高，在第二个边沿采样。

模式、最大时钟频率、每字位数和位序必须按外设数据手册配置。模式不匹配时，常见现象是数据整体错位、位值不稳定或读回固定值。

代码表达的通用结构

// 伪代码：函数名称由具体 MCU、SDK 或驱动决定
spi_config_t config = {
    .clock_hz = <时钟频率>,
    .mode = SPI_MODE_0,
    .bits_per_word = 8,
    .bit_order = MSB_FIRST,
};

spi_init(&config);

cs_set(<片选引脚>, LOW);
uint8_t received = spi_transfer(<发送字节>);
cs_set(<片选引脚>, HIGH);

spi_transfer() 同时完成发送和接收。单纯调用“读取”而不产生时钟通常无法从外设获得数据。

读取寄存器的通用模型

uint8_t tx[2] = {
    <读命令或寄存器地址>,
    0x00  // 占位字节，用于继续产生时钟
};
uint8_t rx[2] = {0};

cs_set(<片选引脚>, LOW);
spi_transfer_buffer(tx, rx, 2);
cs_set(<片选引脚>, HIGH);

uint8_t value = rx[1];
命令格式不是 SPI 总线规定的：寄存器地址、读写位、连续读规则和返回字节位置都由具体芯片协议定义，必须查看数据手册和时序图。

排查顺序

  1. 确认供电、电平和共地正确。
  2. 确认 SCLK、MOSI、MISO 与 CS 没有接反，片选目标正确。
  3. 对照数据手册检查 Mode、位序、每字位数和最高频率。
  4. 从较低时钟开始，用逻辑分析仪观察 CS、时钟边沿和数据位。
  5. 先读取固定芯片 ID 或状态寄存器，再调试复杂连续传输。
  6. SPI 缺少底层应答；读到全 0x00 或 0xFF 时，仍要检查片选、接线和外设是否真实响应。

依据：Linux Kernel 的 SPI 驱动接口、SPI 模式说明与 SPI 用户态 API。

20｜MCP 工具集成与权限边界

Model Context Protocol（MCP）用统一的客户端—服务器接口，把外部知识、工具和可复用提示接入 AI 应用。它解决的是“如何标准化暴露能力”，不是模型本身。

角色与能力

Host承载对话和模型的 AI 应用，管理一个或多个 MCP Client。
Client与某个 MCP Server 建立专用连接，发现并调用其能力。
Server通过标准协议提供工具、资源或提示；既可以在本机运行，也可以作为远程服务运行。
原语作用典型风险
Tools执行构建、查询、写文件、调用 API 等动作。可能修改数据、占用资源或操作硬件。
Resources向模型提供文件、项目状态、文档等上下文。可能暴露敏感内容或过期数据。
Prompts提供可复用的交互模板。模板内容仍需审查，不能替代权限控制。

远程文档服务器与本地工具服务器

维度远程文档 MCP本地项目 MCP
主要用途搜索官方文档、API、示例和兼容性信息。读取项目状态，并执行构建、清理、烧录等动作。
常见传输Streamable HTTP，经网络连接服务端。stdio，由 AI 应用启动本机进程。
依赖网络、服务可用性、认证和服务配额。本机工具链、项目目录、串口和操作系统权限。
数据边界查询内容会发送到远程服务，应避免附带内部代码或密钥。可接触本地文件与设备，应严格限制工作目录和可调用命令。
以乐鑫为例：Documentation MCP 负责检索官方资料；ESP-IDF Tools 本地 MCP 把 set-target、build、clean、flash 等项目动作，以及配置、构建状态和串口列表等只读资源暴露给 AI。二者是“知识来源”和“实际执行”的互补关系，不是同一个服务器。

是否需要自己写 MCP Server

  1. 先列出任务需要的工具、资源、认证方式和数据边界。
  2. 优先复用官方或可信的现有服务器，核对来源、版本、许可证和维护状态。
  3. 只有在现有服务器缺少内部系统接口、专用硬件动作或必要的权限约束时，才实现自定义服务器。
  4. 自定义工具应保持单一职责，使用明确的输入 Schema，并返回可验证的结构化结果。

识别限制层区分客户端、服务器、认证、网络与本机权限
读取错误证据检查状态码、错误正文、日志和 Retry-After
减少无效调用缓存、合并查询、缩小结果与避免重复检索
按策略重试等待配额窗口，采用指数退避并设置上限
现象优先检查处理方法
HTTP 429 或明确提示 quota小时/每日额度、账号身份、响应头。停止连续重试，等待窗口恢复；缓存相同查询并合并相近问题。
401 / 403登录状态、令牌作用域、服务端授权。重新认证或申请最小必要权限，不在配置中硬编码密钥。

不要绕过服务限制：频率限制是服务容量与滥用防护的一部分。不要用多账号、并发轰炸或自动循环规避；若任务需要批量处理，应改用适合自动化的接口或向服务方申请配额。

本地执行的安全基线

  • 把工作目录限制到 <项目目录>，不要默认开放整个主目录或磁盘。
  • 对构建、只读状态查询与烧录/擦除使用不同权限；高风险动作执行前要求人工确认。
  • 使用命令白名单和结构化参数，避免把任意 Shell 字符串直接交给工具执行。
  • 记录工具名、参数摘要、退出码和结果；日志中隐藏令牌、用户名、真实路径和设备标识。
  • 烧录后读取项目状态或串口输出进行验证，不能只依据“工具调用成功”。
